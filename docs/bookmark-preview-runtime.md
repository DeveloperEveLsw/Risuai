# Canonical bookmark pages and independent original previews

The original BookmarkList reads canonical pages of up to100 distinct live members. First/next controls reach the full collection without adding bookmarked bodies to the main message window. Names, saved role, generation information and timestamps belong to the preview's stable source rather than an unrelated loaded row.

Each open list owns a session and each page owns a presentation token. The registry retains one page only. Closing, replacing the page, selecting a different conversation, changing its epoch, or a newer bookmark/body/order/removal event retires the source before another async stage can submit effects. Reads ahead of SSE projection wait for their cursor; they cannot attach older projected settings or variables to a newer body. A changed page token restarts the first page. A late result cannot publish into a reopened list.

The original first CBS, display regex, Lua, Markdown and HTML pipeline receives a separate canonical history window and real ordinals/full count. It retains saved message rewrite provenance from display_message_origins. The main DBState message array remains independent. Unloaded history reads retain the existing explicit failure policy; no fabricated holes or automatic full-archive reads are supplied.

Original list rename/remove and preview saved-message controls use captured stable IDs and revisions. Pending intents keep the existing private preparation, durable outbox, epoch and ABA checks. Another device's edit/deletion invalidates the preview page and reloads current canonical members.

Full-history branching still requires its own server command. The original branch action now rejects partial-window copying instead of silently creating a truncated local branch. This is a temporary explicit limitation, not branch completion. Arbitrary live display bursts, first synchronous CBS, translation/inlay/extensions, metadata/tombstone budgets, real mobile OS behavior and the configured user trial remain required. Schema14 and all15 conditions in [the runtime plan](server-runtime-plan.md) are preserved. No production/private-data access or remote push is included.

Validation evidence and final commit are recorded in the root report/evidence after fresh checks; earlier606 checks prove the preceding history-window milestone only. Launch instructions remain in the runtime plan.
