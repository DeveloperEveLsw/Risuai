# Canonical prefix branching through the original UI

The original message branch button submits one durable `branch-chat` command. It captures the saved message revision, source chat revision/epoch, character epoch, folder collection revision and `createFolderOnBranch` setting revision/epoch. A pending preparation and the durable outbox keep its controls busy without mutating confirmed DBState. Finishing selects the new branch only while the original navigation owner is still current. Unconfirmed source field/variable/display intents and the actual folder/setting dependencies hold branching; an unrelated chat variable does not hold it.

SQLite copies every live source message up to the captured stable boundary, including history outside the browser's100-body window. Positions are dense in the new chat and every copied message receives a new globally unique ID. Bodies are read one at a time in the database worker. A disabled original branch comment retains its source chat/message IDs; an optional structured origin keeps names containing `::` navigable. The browser receives one body-free chat creation event and loads at most100 bodies when it opens the result. Creating a shared branch folder and assigning the source/new chat are part of the same transaction. Existing folders are reused and the branch name is chosen against canonical chat names.

Known copied bookmark/memory anchors are remapped. Anchors to live source messages beyond the boundary are removed; dependent HypaV2 split chunks are removed with their parent summaries. Supa data whose boundary lies in the omitted history is reset. Unknown fields, summary text and already orphaned anchors are preserved without guessing. Current ordinary/local-global variables are copied as upstream does; branching does not reconstruct historical variable state. The new chat is a fresh display occurrence, so source display receipts/origins are not reused.

Revision/epoch and folder/setting conflicts remain visible. Accepted source generation jobs must finish or be cancelled before copying; browser closure does not discard an already durable command. SQLite rollback covers the folder, source assignment, copied chat/messages/variables/bookmark revisions, change journal and command receipt. The schema remains14.

Database work and the identity maps scale with canonical history and metadata. SQLite serializes this transaction in its worker, so a very large branch can delay other database commands even though it does not occupy the browser/HTTP execution thread. The creation event still includes chat metadata; full metadata budgets, broader folder/editor policies, extension/offline/restore/physical-mobile and the configured trial remain required. All15 original completion conditions in [the runtime plan](server-runtime-plan.md) stay unchanged.

Final verification and limitations are recorded in the root report/evidence after checks. No production/private-content access, deployment or remote push is included.
