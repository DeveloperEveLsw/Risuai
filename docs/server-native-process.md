# Native job process isolation

The first hosted designated-character generation completed, but the next job failed at the installed `onnxruntime-node` binding with `ERR_DLOPEN_FAILED: Module did not self-register`. Gemini's original Gemma tokenization imports Transformers, whose Node entry imports ONNX even for tokenization. An independent Node 24.19.0 probe reproduced successful import in the first worker thread and the same failure in the second, without private data or provider calls.

The production scheduler now creates a fresh Node process for each engine job, bounded by the existing concurrency setting. `processWorker.cjs` presents the existing supervisor interface; `jobChannel.cjs` preserves progress, cancellation, final results and IPC flushing. The same execution code runs in that process. Its SQLite client still uses its own state worker, while generation libraries and native addons belong to the child process. A lost supervisor or forced cancellation kills the owned process; the durable scheduler fences its lease and never automatically replays a possibly executed provider request. No Chromium process or browser session is involved.

Synthetic regression exercises four real Gemma-tokenized generations across sequential and concurrent isolated processes, durable provider cancellation, and forced process death under the actual default scheduler. Hosted testing still requires a new explicit validation request after deployment; the prior failed job is preserved.

Process startup and one set of library caches per active job consume more memory than lightweight thread jobs. Concurrency remains bounded (default two), and idle generation processes exit. The original tokenizer algorithm is unchanged. This resolves the observed addon lifecycle boundary; it does not implement all providers, a complete plugin host, persistent shared embedding caches, or universal mobile compatibility.

Related primary references: [Transformers issue with the same first/second worker import behavior](https://github.com/huggingface/transformers.js/issues/651) and [Node native addon worker support requirements](https://nodejs.org/api/addons.html#worker-support). The diagnosis and acceptance evidence above come from the installed runtime reproduction, rather than assuming a reported issue alone proves this deployment's cause.

The next hosted tab-close attempt exposed a separate lazy character lookup defect before the provider call. `readCharacterSnapshot` already starts a WAL read transaction, but called `getCharacter`, which starts another transaction. The read helper now calls `characterView` inside its own pinned transaction. Definition, field revisions, epoch and navigation summaries remain consistent. A read-only regression covers successful repeated lookup, edits, missing identity and rollback after invalid input. Local and hosted Node 24 backend checks pass 206 tests; a direct read of the designated restored character also passes without any provider request. The failed hosted job remains preserved for audit, and a new explicit request is required to verify generation after deployment.
