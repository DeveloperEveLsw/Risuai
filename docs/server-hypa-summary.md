# Original Hypa V3 summary calculations on the server

The upstream `sanitizeSummaryContent`, `summarize` and `getCurrentHypaV3Preset` algorithms are shared by browser and native hosts. The browser keeps the original implementation through thin wrappers. Native summary jobs use the original memory-model provider request, ChatML/default prompts, inlay sanitization and thoughts removal. Single jobs resolve stable chat memos and the selected greeting from a pinned execution snapshot, then optionally run the original CBS/editprocess regex path. Original editprocess Lua behavior returns the input unchanged; no new Lua event has been invented.

`POST /api/runtime/jobs` admits `memory-summary` with `chatId`, `expectedChatEpoch`, `expectedMemoryRevision`, `mode` (`single`/`bulk`) and sorted unique `indices`. Single selects one summary; bulk selects 2–128. Admission validates the memory source. The native worker repeats the revision/epoch check before requesting a provider. Jobs reuse durable admission/idempotency, same-chat serialization, independent other chats, cancellation, leases, fences and provider-output retention.

Calculation stores a preview rather than replacing summaries. Completed previews are read explicitly at `GET /api/runtime/jobs/:id/memory-summary`. Normal status/events/poll omit the text. Calculation completion guards the source aggregate, source history, character incarnation/revision and every configuration resource revision/membership. This conservative resource guard can reject an unrelated settings/module edit. Field-level automatic read tracking remains future work. Original script effects commit atomically with a successful calculation; a script that modifies its own source memory is rejected rather than yielding a misleading preview.

`apply-memory-summary` and `dismiss-memory-summary` commands accept only stored `jobId`, `chatId` and `expectedChatEpoch`. Apply checks source memory/history/character again, uses the server's stored output and preserves unknown aggregate/summary fields. Bulk preserves the first summary's important/category/tags/unknown properties, unions memos and removes the other selected summaries. Applying and recording disposition share one SQLite transaction. Lost acknowledgements and repeated request IDs do not apply twice. A stale apply keeps the paid result readable. Dismiss is durable. A failed calculation can be retried only against its unchanged captured memory selection; partial script effects cannot be recovered as a successful summary.

The relational schema remains version 21. Summary/category/tag data still lives in the `hypaV3Data` aggregate; no item-level relational rows or merging are claimed. Browser-controller APIs exist, but the original Hypa V3 modal controls, durable result re-opening UI and full automatic Hypa V3 context-selection pipeline have not yet been integrated. Existing automatic SupaMemory tests remain separate. Group summary jobs require an explicit member context and currently reject group owners. WebGPU local summary models require a server capability and fail explicitly before provider access. These are outstanding parts of the original 15 requirements.

Display Lua diagnostics now retain the underlying bounded failure message in a failed draft, and the original render wrapper includes it in its error. Failed calculations continue to submit no persistent effects. This improves diagnosis of the user's reported generic display-Lua error; it does not establish that enabling Hypa caused that error. No live saved prompts/stories/chat bodies/scripts/credentials were inspected.

Validation uses authored synthetic fixtures and loopback fake providers. TTS development/verification is excluded by the user's explicit instruction. A newly requested deployment is a separate authorized operation, preserving the database/assets/auth mount with an opaque snapshot and isolated startup/rollback verification; it does not complete the broader goal.
