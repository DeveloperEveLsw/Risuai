# Durable provider response choices

Entity-mode response arrows now select the strings actually retained by the original `addRerolls` port. A cached selection changes only the current assistant message's `data`, keeps its stable ID, and synchronizes through ordinary durable commands and events. Variables, metadata, generation information, output triggers/Lua and statistics are not rewound or executed again. A cache miss on **next** admits one new native reroll job; it follows the existing original reroll boundary and independent server lifecycle.

This records the schema17 provider-choice foundation. The later [schema18 regenerated-batch extension](reply-batch-runtime.md) adds the original screen's separate immutable `Message[][]` response history, provider-first selection, complete single/group tail replacement and prefix ownership. Its additional limits and current validation are documented there. All15 completion requirements in [the plan](server-runtime-plan.md) and the active local-only goal remain unchanged.

## Original semantics and storage

The differential test reads the public baseline `f9728b14c733d073168d8d0c6a8f34f8febf0304:src/ts/process/prereroll.ts` from local Git and checks the current file remains identical. Previous/next selection retains the original increment past the cache, decrement unless negative, empty-string cache miss and index after a failed new request. In particular, selecting candidate0 can replace later listener output with the earlier cached string, as the original screen does.

Actual native tests run the original provider/CBS/regex/Lua pipeline with authored provider ports. Nonstreaming `gpt4o` requests send `n=3` and retain three strings after edit-output regex/Lua. The tested original OpenAI streaming wrapper receives three indexed choices but emits only key0, so its retained cache contains one raw string before output processing. This existing wrapper behavior is preserved and reported; the new storage does not invent unavailable candidates or rerun their scripts.

Schema17 adds `reply_choice_sets` and ordered `reply_choices`. Ownership includes chat ID/epoch, message ID and generation ID; message row and choice-head revisions guard each move. Native final persistence and supported full-result recovery capture the collected cache in the same transaction as canonical effects. Recovery preview rolls it back with its savepoint. A missing cache can create a fallback head for an imported/legacy reply. The parent command, generated child ID, head update and events commit together, and replay returns the original child receipt.

`GET /chats/:id/choices?messageId=…&revision=…&epoch=…` returns a body-free header. The DB still evaluates JSON fields, but the header path does not copy or parse the full message body in JavaScript. `move-reply-choice` never accepts client-supplied candidate text. Same-chat queued/running work prevents selection, and native-admission barriers retain unresolved device configuration/variables/fields. Conflicting peer intent remains visible in the existing outbox/status UI rather than becoming an additional model request.

## Trial and remaining limits

Run `pnpm build:native`, the entity-mode web build, then the built UI test with `RISU_DISPLAY_WORKER_BUILD_PATH="$PWD/dist" node --test server/browser/replyChoicesUi.test.cjs`. All data, credentials and provider responses in that fixture are authored locally; it does not use the live service or real provider accounts.

Existing pre-schema17 completed jobs are not automatically backfilled from their stored results. The schema18 extension supplies separately regenerated single/group batches under its documented ownership policy. The per-chat local click guard does not queue rapid clicks while a move waits for receipt projection; visible text can precede its release, and its pending-feedback treatment remains a responsiveness follow-up. A cached selection conservatively waits behind unresolved device configuration even if it ultimately needs no generation. Arbitrary extension-created messages sharing a generation ID currently get independent message-owned heads instead of the original global index. These are explicit limits, not complete original-UI compatibility.

Caches survive individual message removal for future batch restoration but are deleted with their chat; no historical candidate-body listing API is exposed. Retention/pruning/export policy is unfinished. Building the generation lookup index during migration scales with the stored message archive, and choice storage duplicates result text. No constant-time migration, representative speed or physical-mobile claim is made. Schema17 is forward-only: an older executable rejects it, so rollback requires a matching pre-migration DB snapshot.

Continue with fast repeated-click feedback and the remaining continuation/read dependencies, extensions/import/export/asset/storage policies, physical devices, representative input latency/long tasks and complete configured trial. No production access/query/deployment or remote push occurred.
