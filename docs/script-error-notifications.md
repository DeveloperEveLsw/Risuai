# Script error notifications and setup confirmation

The reported `setupConfirm` job failed because the native extension host did not provide `alertError`. Its setup validation calls `pcall(alertError, triggerId, message)` when required selections are missing and then returns. The original browser function shows a message and does not throw. The server instead recorded a missing capability in the execution context, so catching that exception in Lua could not restore the transaction's health.

The reported job `1a89da1e-3d90-4740-8c57-6c45e50b1c9a` has state `failed`, code `ENGINE_ERROR`, and message `Execution capability errors: Server capability is required: alertError`. The inspection found no complete write set, no provisional messages and no retained provider outputs. The provider-call metadata is absent, which is not itself a measurement of call count. `RESULT_NOT_RECOVERABLE` is the subsequent recovery guard, not the initial failure. The failed invocation remains unrecoverable; do not fabricate a complete transaction or replay its button automatically.

The native worker now binds script `alertError` to the existing durable notification publisher. The extension adapter handles normal and error notifications with the same health checks. Text normalization follows the original error alert: trim text, use an Error's message and ignore the literal `{}`. Notifications share the existing bounded, ordered, ownership-checked queue and generic browser notification panel. This adds no schema or severity field and does not reproduce the browser error-modal styling. It does not wait for acknowledgement to complete a job.

This change does not replace the generation engine's fatal `alertError` handler. Lua execution failures, absent capabilities, notification size/count limits and storage failures still prevent canonical effects from being saved, even when a script catches the immediate exception. Existing recovery and incarnation guards remain intact.

The synthetic confirmation fixture covers an incomplete selection returning normally with an explanatory notice, keeping the form open and saving no invented choice/message; a subsequent explicit selection and confirmation closes the form. Native tests cover mixed alert ordering, caught notification floods and actual SQLite notification-storage failures. The built original HTML/Lua UI test issues an error alert after all tabs close and verifies retained delivery, peer acknowledgements and restart replay. The two targeted fixtures fail with the prior implementation.

After deployment, a user should close the old result dialog, refresh, select the required fields and explicitly press confirmation again. A missing field should produce its normal explanation rather than a failed job. This is a new invocation, not recovery of the old one; no installed script or character data is rewritten.

The current patch is developed and checked locally. The prior local-only goal prohibits production deployment until the user decides; an explicit deployment decision is required separately. The targeted diagnosis used the user's reported job metadata and the necessary setup function only. No provider request or button replay was initiated. All fifteen conditions in [the plan](server-runtime-plan.md) remain active; TTS remains excluded by the user's instruction.
