# Persistent display source intents

The original `@@inject` and `<inject>` display regex operations save the processed text before removing the matched marker from the displayed text. Entity mode now collects that source write privately and admits it after final CSS/sanitization and the current presentation owner's acceptance. Ordinary regex processing remains upstream code.

The request identifies the captured message ID and revision, rather than a UI row or storage position. A real synthetic partial window contains 100 of 110 messages after two deletions: UI row 99 identifies `m-111`, ordinal 109, position 111. Its processed pre-removal text reaches that source once. Other message fields remain intact; writes to other rows, message fields, or the history collection still fail explicitly.

Original CBS scopes created later in the same presentation read the private proposed source. Forked owners retain independent proposals. First CBS, regex, CSS and Lua variable reads join one admission; read-only Lua also retains its reads when a later regex proposes a source write. Provisional variables do not authorize persistence. Different admission provenance cannot reuse an already accepted owner promise.

The existing server command transaction checks epochs, the external input clock, source revision and variable read/write CAS, then saves bounded variable edits, at most one source edit, the receipt and source origin atomically. The existing 128-key and 256 KiB UTF-8 limits include source text. A busy generation rolls back preceding variable effects. Identical source text preserves its revision. Legacy variable-only receipt hashes remain compatible.

Schema 13 stores the latest origin in a relation to the message and display receipt. Browser snapshots join origin headers only for their bounded message page; server generation snapshots retain their existing format. SSE and the partial read model carry the same header separately from the original message payload. Matching revision, epochs, input clock and Lua code hash suppress repeated setters and source admission after an echo, another device or reload. A new external input permits a new occurrence. External message edits clear the projected origin; chat deletion removes its related receipts and origins.

Actual original UI, Worker, IndexedDB, HTTP and SQLite checks cover regex-only and joint Lua/source admission, two independent contexts and reload. A source proposal is not saved after display cancellation or a later partial-history CSS error. A real command transport gate leaves the accepted request in IndexedDB while SQLite stays unchanged; closing the tab and reopening its context replays it once.

The migration and full regression evidence are recorded in `docs/local-validation.json` and the workspace's `evidence/display-message-validation.json`. The original capability-gap reproduction and intermediate server checkpoint remain separate historical evidence. A real CLI check also found a hard-coded health schema: health now reads the actual SQLite version through its existing database worker.

This does not complete arbitrary persistent outer CBS setters, variable collection revision admission, browser-only plugin policies, unloaded-history operations, nondeterministic or non-idempotent presentation scripts, translation/DOM/inlay lifetime, physical mobile/offline acceptance or the configured user trial. A source origin prevents duplicate persistent effects; it does not make arbitrary user scripts pure. All 15 original requirements remain active. Production was not accessed or changed.
