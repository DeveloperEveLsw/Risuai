# Durable regenerated reply batches

The original response arrows now retain a separate, server-owned history of complete regenerated single/group response batches. Two devices share the same selected batch after reload. Selecting a saved batch restores all message fields and stable IDs, with new revisions above deletion tombstones, and publishes one tail replacement. Unchanged prefix messages keep their browser objects and DOM. Selection does not call providers or rerun the native output regex/trigger/Lua pipeline, and does not rewind variables, metadata, character definitions or statistics.

This extends [provider choices](reply-choice-runtime.md). All15 requirements in [the plan](server-runtime-plan.md) remain active; production was not accessed, queried, stopped, deployed or pushed to. All fixtures and credentials are authored locally and providers are synthetic.

## Original semantics and deliberate repair

The public original `DefaultChatScreen.svelte` first calls `Prereroll`/`PreUnreroll` on the last message's generation ID. A truthy provider candidate changes only that message's data. On a cache miss it then tries the adjacent `Message[][]` snapshot; next at the end generates a new native reroll. Provider indices advance/decrement with the original empty-string and negative-index rules, even when a later batch selection succeeds. These phases remain in that order.

Saved batches are immutable snapshots at successful persistence. Later candidate selection, text editing and continuation do not rewrite them. Moving away and returning restores their original complete payloads, including generation information, timestamps and unknown JSON fields. Current side effects stay current.

The original screen overwrites `msgs[msgs.length - rerollData.length + i]` without removing the prior batch. When group counts differ this can mix responses or overwrite prefix rows; its initial lazy baseline also contains only the last group message. The server deliberately replaces the entire owned tail, captures the entire original speaker batch and scopes history to one chat. An equal-length differential test executes the actual public-original assignment loop and compares complete message payloads. Unequal-length tests verify this repair instead of asserting the original corruption.

## Relational ownership and transactions

Schema18 adds `reply_batch_sets`, ordered `reply_batches`, ordered immutable `reply_batch_messages`, and one `reply_batch_heads` pointer per chat. The header identifies a set/revision, selected position, count and whether its live prefix/tail still match. It never returns saved bodies.

Successful modern send stores its newly generated assistant tail and excludes the admitted user input. A new send resets the active history. Modern reroll captures the actual native contiguous assistant tail before applying its complete write set. If the previous history owns the same prefix and selected message IDs, the new batch appends to it; otherwise a new independent set saves the actual prior tail and new response. The original native reroll boundary remains unchanged.

Capture, canonical writes, collected provider candidates, final job status and events share the existing ownership-checked transaction. Failed, cancelled and provisional output do not change history. Supported complete retained-result recovery captures it once; preview rolls every new history row and event back with the existing savepoint.

`move-reply-choice` now captures content revision and batch identity/revision in addition to message/epoch/provider-head guards. These guards reject a concurrent device's intervening content change before any cache advance or selection. A fresh header permits prefix text changes while preserving that current text. Ownership pins the prefix's last ID/count and selected tail's ID order: moving/removing that boundary, changing its count or replacing tail IDs invalidates it. Earlier prefix changes that retain the boundary/count remain current; this is not a complete fingerprint of every earlier message or full read-dependency tracking. Same-chat pending jobs retain the existing busy policy and other chats are independent. Request replay retains the original receipt after reopen.

An adjacent batch replaces only its owned suffix. Shared live IDs update in place; resurrected IDs receive monotonically greater revisions than their tombstones. An archived ID already owned by another chat or prefix rejects the entire transaction. One `reply-batch` event carries the complete replacement, positions, dense ordinals, count, epoch and chat revision. No individual removal/addition events expose an intermediate empty or mixed batch during selection.

## Browser projection

DBState applies the complete batch before rendering once. The message array and unrelated prefix proxies survive. Removed variant bodies leave the browser message cache rather than accumulating every archived batch. Held older pages and repeated events cannot restore stale rows or ranks.

A historical window whose prefix survives keeps its loaded bodies and receives only the new count; it does not jump to the response tail or read the archive. A window at the latest response stays bounded by its configured page size. If a replaced batch removes the entire visible historical window, one bounded page recovers a surviving prefix or latest view. Bookmark previews retire their old message/ordinal observations on batch replacement. Existing display ownership/input clocks fence retired rendering work. Original display scripts can still run for the new presentation under their guarded admission policy; this is separate from rerunning native output effects.

The SQL cases cover unequal groups/stable IDs/side effects, immutable full payloads and the actual original assignment loop, provider-first selection, two DB workers/receipt replay/prefix guards, provisional/failure/cancel/recovery/preview, transaction rollback/ID collision, send reset/non-tail writes, schema17 migration and obsolete unadmitted commands. Read-model cases cover atomic publication, unchanged prefix identity, dense ranks, stale snapshots/replay, unloaded historical tails and bounded latest/deleted-window recovery.

A real native group with original output regex, triggers and Lua generates two replies, disables one member, then regenerates one reply. Repeated previous/next selection restores both shapes with the same three provider calls and unchanged canonical effects/statistics. Actual built original UI tests use two authenticated browser contexts, response arrows, peer synchronization, immutable metadata, prefix DOM, reload, lost receipts, all-tab exit and worker crash/service restart. A previous read model fails the new projection tests; the candidate is restored byte-for-byte before the final checks.

See [machine-readable validation](reply-batch-validation.json) and root `evidence/local-reply-batch-20261004.json` for the exact final source and acceptance results. The existing causal barrier correctly held it; the final fixture first proves that rejection, then resolves it using the actual status UI's request-cancel button. The expanded group fixture also needed the post-selection monotonic revisions as its crash baseline, and the original send UI's terminal readiness before clicking an arrow. Its previous premature click was ignored by the existing busy guard. Initial fixture mistakes and assertion corrections are retained separately from passing acceptance logs.

## Limits and remaining full scope

- Capture supports modern native send/reroll whose response is a contiguous assistant suffix. Arbitrary scripts that delete non-tail rows, introduce user rows into the replacement, or structurally change its prefix retain their canonical effects but clear incompatible history. Their general response-history semantics remain unfinished.
- A continuation that adds messages or any structural edit can invalidate the saved tail. Previous selection reports a conflict instead of overwriting unrelated messages; next can start a fresh native history. Complete original continuation/manual-cache behavior needs a separate policy. Clones, branches and imported pre-schema18 conversations do not inherit old batch histories automatically; their first supported reroll captures a baseline.
- Existing schema17 provider-only receipts replay unchanged. Previously unadmitted old-client commands without the new captures reject and remain reviewable; no unsafe default guards are inferred. Client/server versions must be delivered together. Migration preserves old canonical data, identity and jobs but does not backfill old batch bodies. An older executable rejects schema18; rollback requires its matching DB snapshot.
- Histories duplicate response text and currently persist with the chat. Retention, source-job pruning, portable export/import, global storage budgets and archive limits remain unfinished. Header ID checks avoid body decoding, but indexed prefix counts still scale with history length. One batch event is subject to the existing bounded JSON policy; no unlimited output claim is made.
- The local in-flight click guard still ignores additional clicks until command settlement; visible text can precede that settlement. Pending feedback and a clear rapid-click policy are the next responsiveness work. Unresolved configuration/conflict barriers remain conservative.
- Full read dependencies, general extensions/editors/import/export/assets/offline policies, physical mobile devices, representative input latency/long tasks and the complete configured user trial remain required. These checks do not prove universally fast rendering or all-card compatibility.
