# 모델 응답 수신 후 스크립트 실패의 원문 보존

아래는8ce0bc5/schema20의 구현·검증 이력이다. 최신 schema21의 관계 행 저장과 작은 상태 조회는 [후속 계약](job-output-relation.md)을 따른다. 실패 원문 확인·부분 저장 차단·자동 재요청 금지 정책은 유지한다.

공개 코드와 합성 DB로 확인한 로컬 후속이다. 운영 배포 bd9b167/schema20의 상태를 새로 조회하거나 변경하지 않았다. 기존15완료 조건과 전체 개발 목표는 계속 active다. 실제 카드·설치 스크립트·프롬프트·대화·인증값은 읽지 않았고 실제 모델 호출도 없다.

## 확인한 문제와 변경

실제 native worker가 합성 모델 응답을 받은 뒤 출력 Lua의 객체에 `gsub`를 호출하면 ENGINE_ERROR로 끝났다. 대화/변수의 부분 저장은 막았지만, 추가 처리 전 모델 응답은 기존 보존 결과 화면에서 확인할 수 없었다. 수정 전 실제 worker 검사의 실패 로그를 보존했다.

서버 `requestChatData` 포트에서 파싱된 응답을 추가 출력 처리 전에 작업의 private checkpoint로 저장한다. 일반 응답·여러 후보의 역할/본문·스트리밍의 누적 후보를 다룬다. 원래 응답 객체와 청크는 그대로 처리기로 전달한다. 원본 CBS·정규식·트리거·Lua·요청/생성 알고리즘을 바꾸거나 객체를 문자열로 강제 변환하지 않는다.

실패/취소/중단 뒤 원본 UI의 ‘보존된 응답 확인’에서 추가 처리 전 응답을 읽거나 복사할 수 있다. 읽기 전용 textarea이므로 HTML·CBS·Lua·이미지 처리를 실행하지 않는다. 파싱된 모델 응답의 수신 완료 여부와 전체 작업의 처리/저장 완료 여부는 다르다. 원문만 있는 작업에 ‘전체 결과 복구’를 허용하지 않으며, 기존의 완전한 write set 복구 조건을 그대로 유지한다. 모델 자동 재요청은 없고 기존 명시적 새 요청은 별도 실행이다.

## 저장과 생명주기 계약

- 기존 schema20의 `jobs.progress.providerOutputs`에 저장한다. schema 변경/이관은 없다. 소유자·fence·lease 확인과 checkpoint/journal 원자성은 기존 `writeJobProgress`를 따른다.
- 일반 응답은 처리기로 돌려주기 전에 보존을 기다린다. 스트리밍은 첫 파싱 청크를 전달하기 전에 저장하고 이후 약250ms 간격으로 합친다. 정상 EOF는 완료로, 소비자 취소·처리 실패 후 닫기·중단은 미완료로 보존한다. 닫을 때 마지막으로 소비한 합쳐진 청크도 저장한다.
- 원본 파싱 스트림에 reader 하나만 사용한다. tee나 끝까지 받는 별도 소비자를 만들지 않는다. Lua가 첫 청크에서 실패하면 그 시점까지의 원문만 남으며, 서버가 보내려던 나머지 응답을 확보했다고 주장하지 않는다. 강제 종료에서는 마지막으로 성공한 checkpoint만 남는다.
- 표준 상태 조회, 전체 Job 조회, 접수 영수증, 취소 응답과 journal 이벤트에 이 새 원문 필드를 넣지 않는다. 실패한 작업의 명시적 결과 조회에서만 원문을 제공한다. 기존 일반 progress 메시지는 유지한다. journal에는 기존 Job ID/진행 버전 포인터만 남는다.
- 성공한 canonical 저장과 같은 트랜잭션에서 원문 복사본을 제거한다. 실패·취소·중단에는 보존한다. 프롬프트·요청/응답 HTTP body·헤더·스크립트 상태는 이 DTO에 포함하지 않는다.
- 작업당 최대64개의 의미상 `requestChatData` 호출, 응답당 최대64후보, 모든 원문 DTO의 JSON UTF-8 합계4MiB다. 65번째 호출은 provider 호출 전에 차단한다. 예산/형식/보존 저장 실패는 처리를 실패시킨다. 기존 전체 progress의16MiB 제한도 적용된다. 이는 전체 heap·DB·WAL·디스크·작업 누적량의 상한이 아니다.

## 검증과 한계

검사는 mock 반환만으로 대체하지 않고 실제 native Lua/HTTP 파싱/SQLite/서버 API와 배포용 원본 UI를 연결했다. 입력/요청 오류는 합성 provider0회, 출력 오류는1회다. 일반 출력 실패, 스트리밍 중 첫 출력 실패, strong 모드에서 EOF 뒤 실패를 구분하며 모두 대화/변수 부분 저장을 차단한다.

두 인증 브라우저가 열린 상태에서 합성 스트림을 시작하고 모든 탭을 닫은 뒤 실패하도록 했다. 로컬 서비스 재시작 후 두 브라우저가 같은 원문을 읽고 HTML 미실행·복구 버튼 없음·DB/커서 변화 없음·provider1회만 실행을 확인했다. worker 강제 종료/서버 재시작과 HTTP 취소에서도 미완료 원문이 남고 자동 재실행하지 않는다. 실제 SQLITE_FULL로 큰 checkpoint를 실패시켜 이전 보존 원문·대화·커서가 유지되는 것도 검사했다. 형식 위반·중복 후보·UTF-8/JSON escape/합계 예산·오래된 소유권은 별도 확인했다.

사용자가 보고한 주식회사 넥서스v2.5의 메시지 전송 오류와 같은 `nil value (method 'gsub')`는 객체에 문자열 치환 메서드를 호출해 재현할 수 있다. 실제 카드/모듈·변수·콜백·Lua chunk6703의 원인은 미확정이다. 이 변경은 해당 스크립트 오류의 해결이 아니며 보내준 대화 내용은 문서/증거에 기록하지 않는다. 이미 실패한 과거 작업에 없던 원문을 재구성하지도 않는다.

parsed text만 보존하므로 reasoning/이미지/도구 호출 등 모든 provider 원시 필드의 보존을 보장하지 않는다. 일반 플러그인 host, 포트 밖 호출, 모든 보조 생성 경로의 실제 카드 호환도 완료한 것이 아니다. 저장 공간이 이미 가득 찼거나 첫 checkpoint 전에 프로세스가 죽으면 보존을 보장할 수 없다. 저장된 원문을 후처리부터 다시 실행하거나 대화에 수동으로 승격하는 기능은 없다.

checkpoint 추가 쓰기·직렬화 및 상태 조회의 JSON 투영 비용에 대한 새 지연/long task 측정은 아직 없다. 이전 모바일모사 약2.28초/208ms 결과는 이전 후보의 근거다. 성능·전체 읽기 의존성·일반확장·보관/import/export/에셋·총저장예산·실물 모바일·전체 사용자시험을 계속한다.

현재 후보의 검사 수치/소스·아티팩트·로그 지문은 [검증 기록](provider-output-validation.json)에 둔다. 격리 실행은 [원본 UI 로컬 시험](risu-browser-integration.md)을 따른다. 합성 fixture의 정규식/Lua를 직접 개인 카드에 적용하라는 의미는 아니다.
